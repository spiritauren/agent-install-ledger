## 问题

AI agent 现在随时能装东西：`pip install`、`brew install`、`npm install`、下载一个二进制、`playwright install`。每一次都「只是装一个」。一年之后，你的硬盘里堆着一批你说不清用途的软件：

- 为一个一次性任务装的 700 MB 运行时，活到了今天
- 装过、用过、忘了，也没删
- 想删，但不确定谁在用它

问题从来不在「装」。**问题在于没人记账。**

## 它管哪一栏

清理工具负责删文件，依赖工具负责出清单，安全工具负责扫包。**它们都不留的是这一栏：这个是什么、为什么在这儿、能不能走了**——以及「装之前先想一下」和「定期回头看一遍」**该在什么时候发生**。

那条链就是这个仓库。

## 第一段 · 闸门

安装之前，agent 必须先回答三个问题。任一答「否」，就是：别装，另找办法。

1. **真的需要吗？**
2. **有更轻的替代吗？**（用户级胜过系统级；小包胜过大包）
3. **它的卸载命令，你现在写得出来吗？** 写不出来，说明你还不清楚自己在装什么。

然后，**落地那一刻就把那一行写上**。闸门管「要不要装」，那一行管「这次装完了没有」。

## 第二段 · 台帐

每个安装物一行，十一个字段。

| 字段 | 说明 |
|---|---|
| 名称 | 安装物名字 |
| 作用简述 | 这东西本身干嘛的（一句话，说人话） |
| 安装日期 | YYYY-MM-DD |
| 安装原因 | 为哪个项目/任务装的 |
| 关联项目 | 对应项目或任务 |
| 安装位置 | 绝对路径 |
| 占用空间 | 它真正占掉的盘：对安装物跑 `du -sh`，**再**加上它拖进来的依赖和它自己的缓存目录 |
| 留存性质 | 临时 / 阶段性 / 长期 |
| 可删除原因 | 为什么现在可以删（复审时填） |
| 卸载命令 | 怎么彻底删 |
| 状态 | 在用 / 可清理 / 已删除（+删除日期） |

注意大多数人会漏掉的那两个字段——**「可删除原因」和「卸载命令」**——正是让一年后还能清理的那两个。没有它们的台帐是**清单**，不是台帐。

## 第三段 · 复审

1. **扫描** —— 读台帐，并用 `du` 把每项重新量一遍。台帐永远是滞后的。
2. **报告** —— 逐项：作用、占用、对应项目完没完、留还是删、为什么。
3. **问人** —— 用户拍板。**在那之前什么都不删。**
4. **彻底删** —— 删**安装物本体 ＋ 它生成的工作文件**（缓存、临时数据）。**保留成果物。** 走系统废纸篓，不用 `rm`（macOS 15 起是 `trash`，其他平台如 `gio trash`）。

### 关键的那条线

> **删工作文件，留成果物。**

缓存目录是垃圾。那份缓存帮着做出来的报告不是。这条线错一次——连工具带一个月的工作一起删掉——人就会学会「再也不清理了」。

两个桶是显而易见的。出事的是第三个：

- **成果物**——留。
- **缓存与临时文件**——删。
- **其余的**——喂出成果物的那个脚本、某个工具自己的数据目录、图表背后那张源 CSV。**这类要单独列出来，一个一个确认。** 判据不是「它是不是最终产出」，而是**「它能重新生成吗——以及这是不是唯一一份？」**

## 它划下的五条线

其中三条是本仓库自己的。另两条是通行做法——它们出现在这里，是因为**规则才能让它们在每一次安装上真的发生**，而不是等人想起来。

1. **在装之前问，不在装之后解释。** 闸门跑在**安装前**，这样「不装」这个答案才还来得及。
2. **量，不要估。** 对真东西跑 `du`——但记住 `du` 只报**本体**。依赖与缓存是**另外**加的，这是有意的。厂商写的下载体积会骗人，你自己加出来的那个数不会。
3. **趁你还记得，把原因写下来。**「可删除原因」是写给未来的你——那个人会不同意今天的「不需要了」。
4. **删工作文件，留成果物。** 整份文档里唯一一个**一旦清空废纸篓就再也回不来**的错误。
5. **删之前，停下来问人。** 自动发现可以，自动删除不行。

## 适合 / 不适合

**✅ 适合**：你在一台自己的机器上跑着有 shell 权限的 agent，而且你已经有过「这一堆装的东西到底是干嘛的」这种时刻。

**❌ 不适合**：你装软件是有意为之、很少装、每样都清楚。**那你已经有这份台帐了——它在你脑子里。**

**不覆盖**：复现环境（`brew bundle dump`、`pip freeze`）——不同的活儿，而且做得很好；**台帐不是 lockfile**。

## FAQ

**我已经装了 200 样东西了，要补录吗？**
不用。从下一次安装开始记。之前那些恰恰就是**复审要处理的对象**——而且复审不需要一份完整的台帐才有用。

**有什么能拦住 agent 不遵守它？**
没有。这是一条规则，不是一个沙箱。它只是让正确的行为成为阻力最小的那条路。真要有强制力，得配合你的 harness 本身能给的东西。

**台帐到底放哪？**
放你本来就会看的地方。Markdown 文件、表格、一个 issue、一个数据库都行。**字段是重点，存储不是。** 合成示例见 `LEDGER.example.md`。

**一样东西永远留着，算失败吗？**
不算。「留」是一个正当的结果——复审存在的意义，是让「留」变成一个**决定**，而不是一次疏忽。失败从来不是拥有东西，是**不知道**。

**如果 agent 半夜没人看着时装了东西呢？**
它照样得写那一行。**恰恰是这种安装，台帐最值钱**——因为当时没有人在看着。

## 一个提醒

这是一条**给 agent 的规则**，所以只有 agent 真的读到它才管用。也就是说它必须放在 agent 本来就会看的地方——技能目录、system prompt、项目规则文件。**一条没人加载的规则是文档，不是机制。**

复审同理。如果永远没人说「复审安装」，第三段就永远不会跑，你手里又变回一堆。**这条链的好坏，取决于它最弱的那个触发点。**
